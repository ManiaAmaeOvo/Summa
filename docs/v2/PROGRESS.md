# Summa 2.0 实施记录

## 基线与范围

以 `main` 的 `f70d075`（v0.4.2）为稳定基线，在
`codex/summa-2.0` 开发。沿用 Flutter、Riverpod 和 Drift。当前开发构建为
`2.0.0-dev.2+8`，位于 Phase 1 财务核心阶段。

## 应用标识与迁移

- Android 应用 ID、namespace 和 Kotlin 包使用 `com.maniaamae.summa`，
  Dart package 使用 `summa`。旧包和新包可并存，各自保管应用文件。
  跨包迁移时，在旧版「设置 → 数据与备份」导出完整 JSON 到应用外，再从新版的
  同一入口恢复。先核对账户余额、历史记录和关联，再决定是否卸载旧版。
  主题、语言等设备偏好和旧应用内的本地备份列表需要分别管理。
- 应用默认使用 `summa.sqlite`。当前私有目录已有旧数据库文件时，仍可原址
  打开。Schema 8 将历史交易回填到持久化分录表，保留交易 ID、金额、时间、
  币种、备注、账户、目标账户和软删除状态。旧交易默认已入账。
  迁移和 SQLite 版本更新在同一事务内提交。
- 完整备份写出 `summa_full_backup` Version 2，包含状态、退款原交易 ID、
  每条有序分录及软删除记录。兼容上述标记的 Version 1 和旧版
  `ledgerpro_full_backup` Version 1。恢复旧备份会生成等价分录。
  合并时若旧快照覆盖同 ID 的新版待入账、拆分、退款或已关联退款的原消费，
  整次恢复会回滚。恢复也会校验分录平衡及有效的退款关系。
- 普通账单 JSON 仍可按 Schema 1 导入和导出。包含拆分、待入账或退款明细的
  报表 JSON 使用 Schema 2 供分析，完整往返使用「数据与备份」中的完整 JSON。

## Phase 1 已交付

- `ledger_entries` 保存交易，`ledger_postings` 保存按币种平衡的分录。
  分录使用整数最小货币单位，借方为正、贷方为负。余额及负债走势读取账户分录。
  软删除保留原分录，余额及已实现报表只读取已入账、未删除的交易。
- 新增或编辑消费时可添加多个同币种付款账户。首个账户承担总额扣除其余付款后的余额，
  每笔付款都必须为正数，同一账户只能出现一次。资金检查逐账户执行，交易与分录一起
  保存。
- 已入账消费可从交易菜单记录部分或全额退款。每笔退款退回所选原付款账户，
  一次消费可分多次退款。待入账退款也占用该账户的可退额度，删除后释放。
  已入账退款在退款发生日冲减原分类支出，并增加资产或冲减信用账户负债。
  若原消费已经还款，信用账户可因退款形成贷方余额。
  仍有关联退款时，先处理退款再修改或删除原消费。
- 新建交易和退款可选择「保存为待入账」。交易列表标明状态，可从交易菜单确认入账。
  待入账可先保存分录与金额，即使当前余额不足。确认时检查账户可用性及资金或待偿
  负债条件。重复确认保持同一笔已入账记录。
- 旧数据的缺失对方账户、币种冲突等异常继续用 `needs_review` 标记，保留旧版
  余额效果。当前表单和汇总沿用人民币口径，拆分和退款采用同币种原账户结算。

1. 完成 Phase 1 剩余财务核心。补充资金归属、原始和结算金额、跨币种估值、
   应收款、分类拆分和冲销。为历史歧义提供待复核入口。余额校准仍沿用旧版行为，

3. 交付 P1。实现预算和外部额度、订阅和周期计划、债务与应收款、储蓄目标与资金分配、
   分析、现金流预测和首页体验。计划数据在确认入账后才影响实际指标。
4. 核心稳定后交付 P2 报告、高级规则及导出，完成真实设备与数据迁移验证后准备
   Release Candidate。P3 通知辅助记账留作后续版本候选。

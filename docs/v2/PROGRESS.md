# Summa 2.0 实施记录

## 基线与范围

以 `main` 的 `f70d075`（v0.4.2）为稳定基线，在
`codex/summa-2.0` 开发。沿用 Flutter、Riverpod 和 Drift。当前开发构建为
`2.0.0-dev.6+12`，Phase 1 财务核心已通过阶段验收。

## 应用标识与迁移

- Android 应用 ID、namespace 和 Kotlin 包使用 `com.maniaamae.summa`，
  Dart package 使用 `summa`。旧包和新包可并存，各自保管应用文件。
  跨包迁移时，在旧版「设置 → 数据与备份」导出完整 JSON 到应用外，再从新版的
  同一入口恢复。先核对账户余额、历史记录和关联，再决定是否卸载旧版。
  主题、语言等设备偏好和旧应用内的本地备份列表需要分别管理。
- 应用默认使用 `summa.sqlite`。当前私有目录已有旧数据库文件时，仍可原址
  打开。Schema 6 和 7 的交易按历史规则回填分录。Schema 8 到 9 新增可空
  的结算字段，9 到 10 新增独立的估值设置和汇率表。Schema 11 沿用现有交易、
  账户和分录表，引入资金归属及应收款语义。Schema 12 增加可空财务明细和
  冲销唯一索引，旧交易、余额、分录和估值设置原样保留。缺少内置转账或应收款
  分类的账本在首次记录相应交易时补齐。
- 完整备份写出 `summa_full_backup` Version 6，包含分录、估值、财务明细和冲销
  关联。兼容 Summa Version 1–5 与 `ledgerpro_full_backup` Version 1。
  Version 4 起的覆盖恢复应用备份中的估值设置，Version 1–3 保留本机估值设置。
  合并保留本机估值基准币种，按币种方向取更新时间较新的汇率，同时间保留本机记录。
  若旧备份合并会覆盖该格式无法表达的新交易语义，整次恢复回滚。
  旧币种冲突记录保留原分录与 `needs_review` 标记。
- 普通人民币账单 JSON 继续支持 Schema 1。包含外币、结算、拆分、待入账、退款
  或其他财务明细的报表 JSON 使用 Schema 2 供分析。账本完整往返使用
  「数据与备份」。

## Phase 1 已交付

- `ledger_entries` 保存交易，`ledger_postings` 保存按币种平衡的分录。
  分录使用整数最小货币单位，借方为正、贷方为负。余额及负债走势读取账户分录。
  软删除保留原分录，余额及已实现报表只读取已入账、未删除的交易。
- 新建账户可选择 21 种币种，其中 JPY、KRW、VND 使用整数最小单位，
  KWD、BHD 使用三位小数。记账、退款和余额校准使用所选账户的精度。
  首页、账户和报表可按原币查看对应的汇总。
  [ISO 4217 币种和精度来源](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html)
- 跨币种转账保留来源账户的原币扣款，以及目标账户的到账币种和实际金额。
  可另存银行或平台报价，方向为每 1 单位原币对应多少到账币种。
  实际汇率由两笔金额及各自币种精度计算，以整数分数为准，界面四舍五入至最多
  10 位小数。报价按十进制文本保存。实际到账金额决定目标余额，报价差额
  不自动生成费用或损益。对应字段为 `amount_minor`、`currency_code`、
  `settlement_amount_minor`、`settlement_currency_code` 和 `quoted_exchange_rate`。
- 跨币种转账各写入两笔账户分录和两笔兑换对手分录，使每种币种分别平衡。
  待入账时保存完整结算信息，确认时检查原币资金。转账不计入收入或支出。
  当前借入、还款、退款和拆分支付使用同币种账户。
- 「账户」页提供折算净资产卡片和估值设置。可选择基准币种，并手动录入
  `1 来源币种 = 汇率 × 基准币种` 的直接汇率。不同基准的汇率分别保存，包含
  更新时间。估值以活动账户的已入账余额为准，用个人资产减负债，排除受托及授权资金。
- 跨币种估值使用精确整数计算，全部折算项相加后一次舍入至基准币种最小单位，
  恰好半单位时向远离零的方向舍入。只要某币种有非零的参与估值余额，就会要求提供
  直接汇率。缺少汇率或历史币种精度时，卡片列出对应币种并暂缓显示总额。
  本币按原余额纳入，转账历史结算率继续随原交易保存。
- 新增或编辑消费时可添加多个同币种付款账户。首个账户承担总额扣除其余付款后的
  余额，每笔付款必须为正且同一账户只出现一次。交易与分录一起保存。
- 已入账消费可从交易菜单记录部分或全额退款。待入账退款也占用该账户的可退额度，
  删除后释放。已入账退款在退款发生日冲减原分类支出，并增加资产或冲减信用账户
  负债。仍有关联退款时，先处理退款再修改或删除原消费。
- 新建交易和退款可选择「保存为待入账」。待入账记录可从交易菜单确认，确认成功后
  才影响余额和报表。重复确认保留同一条已入账记录。

## 资金归属与应收款

- 「记一笔 → 支出」可选择「家庭直接承担」。系统按币种使用外部资金分录，
  该资金来源不出现在个人余额或估值里。先转入个人账户的生活费可使用
  「收入 → 家庭支持」，后续从个人账户消费计入本人承担。受托资金仍使用
  独立账户类型，旧亲情卡及其他受托账户保留历史入账方式。
- 本人承担包括个人现金、信用消费和需要偿还的他人代付。可用「他人代付待偿」
  账户记录他人先付的个人消费，支付本金时使用「还款」。报表中的他人代付款为
  本人承担金额的其中项。家庭直接承担和受托资金另列。
- 报表按发生日和币种计算各项金额。总消费包含本人承担、家庭直接承担、受托
  资金及待确认归属，按原资金来源扣减已入账退款。个人现金流取现金、银行、
  钱包分录，剔除本人现金类账户之间的转账，包含借出、垫付、回款与还款的实际
  现金变动。待入账交易在确认后纳入指标。
- 可按对方和币种建立独立应收款账户。「借出」和「垫付」将个人资金转入应收款，
  「收回本金」和「报销到账」将应收款转回个人资金。应收款纳入折算净资产，
  日常可用现金口径仍按个人现金类账户余额计算。借出、垫付、回款均为本金流动。
- 回款按应收账户和流水发生时间校验。确认、历史编辑、删除或合并后若应收本金
  会在任一时点变为负数，整次操作回滚。首次建立应收账户可录期初未收本金。
  单笔 AA 账单可以同时记录自身支出和替他人垫付的应收本金。应收的账期、合同
  和逐笔核销属于 Phase 3。

## 消费结算、费用与账务修正

- 外币消费在「高级记账选项」记录商品原币金额及可选报价。主金额是付款账户实扣
  金额，分类、消费和个人现金流按实际支付币种统计。退款按原付款账户的实际到账
  金额记账。外币消费报价、跨币种转账历史结算与资产估值汇率各自保存。
- 单笔消费同时支持多账户付款、多分类和 AA 应收款。次要分类录入金额，主要
  分类承担自己消费的剩余金额。替他人垫付部分形成应收，仅计入实际个人现金流出。
  普通退款按原分类顺序冲减已支付金额。AA 退款可指定冲减的应收本金，留空时
  先冲减消费，再冲减应收。若冲减会令应收账户历史余额为负，先处理相关回款。
- 转账手续费、还款本金、利息及手续费独立记账。本人现金账户间转账只统计实际
  手续费现金流。对方直接承担本人债务本金时，减少负债并记录外部承担，个人
  现金流、收入和消费保持原账务口径。若仍欠付款方，需要另记对方的债权债务。
- 储蓄账户计入个人流动资产。预付余额作为独立个人资产列示并参与估值。充值
  计入个人现金流出，随后使用预付余额时才计入消费。
- 「账户 → 校准余额」按校准当天写入独立差额分录，可记录原因。随后从交易历史
  查看或冲销，期初余额保持创建时的数值。差额调整排除在消费、收入和个人
  现金流之外。按指定日期核对账面与实测余额及保存检查点属于 Phase 2。
- 已入账交易可以按操作日生成相反分录。原交易、冲销及其关联均保留，同一笔交易
  只能有一条有效冲销。冲销按日期回冲原消费、收入或现金流方向。仍有关联退款的
  消费先处理退款。待入账记录可取消。仍待
  确认语义的旧记录在交易列表显示「待复核」，支持筛选后按原始账单修正。

## 验收与边界

| 验收项 | 校验条件 |
| --- | --- |
| 分录与交易 | 每笔交易逐币种借贷平衡；待入账交易确认一次；软删除和冲销保留历史 |
| 消费、资金来源及应收 | 本人、家庭、受托和他人代付按来源统计；AA、转账费用、回款与退款各自只计一次 |
| 货币及净资产 | 保留原币、实际支付、结算报价；估值汇率独立；缺失币种显示提示 |
| 余额及负债 | 本金、费用、外部代偿、储值及调整按分录核对；拒绝超额回款及历史负应收 |
| 数据安全 | Schema 6–11 升级、旧版备份读取、Version 6 往返、冲销关联和损坏备份原子回滚 |
| Android | Debug APK 在专用模拟器中升级合成账本并操作记账表单；真机与真实账本用于发布前验收 |

2026-11-20 验收结果

- 99 项 Flutter 测试全部通过，静态分析无问题，Android Debug APK 构建成功。
- Android 模拟器从 Schema 11 原址升级至 12，保留原有 7 笔交易、17 条分录、
  13 个账户和两条估值汇率。SQLite 完整性和外键检查通过，所有分录逐币种平衡。
- 实际录入原价 AED 2、实扣 ¥12、其中替他人垫付 ¥4 的账单。待入账时总消费
  仍为 ¥54.45。确认后总消费为 ¥62.45，本人承担为 ¥57.45，个人现金流出为
  ¥65.45，应收为 ¥10。冲销后，总消费恢复为 ¥54.45，个人现金流出恢复为
  ¥53.45，应收恢复为 ¥6。随后校准增加 ¥1，历史中有独立差额分录，报表消费保持原值。

## 后续交付顺序

1. Phase 2 数据可靠性。实现基于真实样本的微信、支付宝及通用 CSV/XLSX 适配器、
   批次与幂等去重、匹配和人工复核、可撤销导入、基础分类以及账户对账与检查点。
2. Phase 3 财务管理。实现预算和外部额度、订阅和周期计划、债务和应收合同与核销、
   储蓄目标及资金分配。规划记录确认入账后才影响实际指标。
3. Phase 4 分析及产品体验。扩展现金流预测、多维分析、账户及交易筛选，完善
   导航和首页。支付渠道、交易对方和原始账单追溯结合导入流程交付。
4. Phase 5 报告及发布。扩展导出与规则，完成真机和真实账本迁移验证后准备
   Release Candidate。通知辅助记账属于 Phase 6。
